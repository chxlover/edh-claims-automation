4. How the agent knows which patient
This was your question, and asking it was the right move — it exposed that the agent/  package could never
answer it.
The patient is not looked up in a database and not typed by hand. The folder name is the record. Every
output folder is already named:
GABAY, MERCEDES BACANI - 000000000021627 - ADM20260913_DIS20260916
      +--- name ----+   +-- hospital no --+  +-- confinement --+
That is the format produced by core/patient_folder_naming.py::build_patient_folder_name() . Parsing
that one string yields the hospital number, patient name and confinement period — exactly the three values
the HBSys clickers need — with no database write and no hardcoded patient data. It also keeps your project
rule that database access stays read-only.

5. Why the decision layer is rules, not learning
The problem vocabulary is already stable and machine-produced, so a learner adds risk without adding
value:
fees_checker.ready_to_generate_xml()  returns a fixed problem list, e.g.
hprofserv.pdoctorsigndate BLANK , ADM date mismatch .
claims_checker  returns a Missing  column of document kinds: CSF, SOA1, COE, DTR, MRF, PBC…
These are exact strings. An exact-match rule table is simpler, faster and testable. A fuzzy learner could mis-
route a claim; a rule table cannot.
Escalation principle. Anything not explicitly mapped is HUMAN. A missing tool must never degrade
into "click something and hope".

7. Work in progress — the orchestrator
Not finished. Do not wire this into the GUI yet. core/pipeline_orchestrator.py  was being
written when the conversation ended, and its test suite was mid-debug.
It contains: per-patient iteration over output\ ; a check → decide → run tool → re-check loop;
the outcomes READY , FIXED , HUMAN , FAILED , REFUSED ; a dry_run=True  default; per-patient
exception isolation; a max_fix_rounds  guard against a tool that never clears the problem; and
an Excel run report.

bugs: the stub problem-source was shared across all patients in one temp directory, so state
leaked between them and every count was doubled or tripled. The fix was to give each scenario
its own isolated directory. That refactor was in progress when the session ended, so re-run the
